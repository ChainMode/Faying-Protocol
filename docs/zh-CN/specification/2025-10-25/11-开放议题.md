## §11 Open Questions

> 本章诚实陈列 Phase 1 协议正文未必须回答、留给协议委员会在 RFC 阶段决议的议题。每条议题给出**当前协议倾向**、**备选方案**与**决议状态**，以便后续 RFC 讨论有结构化的起点。已决议条目（如 Q10 协议命名）保留作为历史记录。

### Q1 Rogue 期间终端的位置上报

- **议题**：iFay 处于 Rogue Fay 状态期间，是否允许终端继续上报物理位置？涉及"隐私 vs 可寻回"的两面拉扯。
- **当前协议倾向**：按 `RevokeReason` 差异化——`human-initiated` / `task-completed` 不上报；`fay-credential-invalid` / `regulatory-order` / `terminal-disconnected` 等可上报。
- **备选方案**：（a）一刀切禁止；（b）一刀切允许；（c）由 HP 在 BOOTSTRAP 时显式预先选择。
- **决议状态**：未决；蓝图第 14 章已显式不下结论。

### Q2 G0 Emergency Override 的不可拒绝路径

- **议题**：在 IF 已被攻击者控制的极端情形下，G0 报文如何确保仍能被 IF 内核执行？
- **当前协议倾向**：协议层强制 G0 报文具有最高优先级（详见 §7.2 / P12 G0 Override 优先级），但承认在 IF 内核已被攻陷时纯协议层手段不充分。
- **备选方案**：（a）硬件级 kill-switch 强制；（b）TPM-quote 双签确认；（c）维持协议层强制并将硬件路径留作生态实现自由发挥。
- **决议状态**：未决；与 Phase 2 / Phase 3 终端接管深度耦合。

### Q3 PQC 默认时间表

- **议题**：Ed25519 + ML-DSA-65 hybrid 何时从 OPTIONAL 提升为 MUST？
- **当前协议倾向**：1.0 仅声明 OPTIONAL（PQC 套件可协商位见 §6.1）；待 NIST 最终标准全部公布后再制定时间表。
- **备选方案**：（a）等待 NIST 全部 PQC 标准定稿；（b）跟随首个标准化签名算法；（c）按 grade 差异化（高敏感场景率先 MUST）。
- **决议状态**：未决；待 NIST PQC 标准化进度。

### Q4 跨人类原型的 iFay ↔ iFay 协作（Phase 4/5）

- **议题**：分属不同 HP 的两个 iFay 协作时，责任传递方式如何确定？
- **当前协议倾向**：1.0 不覆盖；Phase 4 引入 coFay 时再定。
- **备选方案**：（a）发起方负责；（b）接收方负责；（c）按规则分担；（d）必须双方 HP 共同见证。
- **决议状态**：未决；需法律—协议双轨讨论。

### Q5 Ego 偏离的客观判定

- **议题**：协议层是否应规定 `ego-deviation` 的最低判定信号集？
- **当前协议倾向**：协议层只定义 `RevokeReason="ego-deviation"` 的语义与触发后果（§EH.1、§3.6 BBS）；具体判定信号集留给实现自由发挥。
- **备选方案**：（a）协议层规定最低信号集；（b）由 §3.6 Behavior Baseline Service 显式约束；（c）维持当前留白。
- **决议状态**：未决；与 Q13 行为基线标准化耦合。

### Q6 Mandate 续期策略

- **议题**：协议是否禁止"自动续期"的全部形态？
- **当前协议倾向**：禁止全部自动续期形态；每次续期必须经 HP 显式见证（蓝图第 10 章倾向）。
- **备选方案**：（a）允许"需 HP 周期性预签名的有限自动续期"；（b）允许低风险 grade（G3/G4）的自动续期；（c）维持禁止。
- **决议状态**：未决；待协议委员会取舍。

### Q7 离线 / 弱网环境

- **议题**：在 RR 不可达的边缘场景（无人机断联），是否允许"限时自治 + 回连后强制对账"的弱化模式？
- **当前协议倾向**：通过 Endorsed_Mandate（§7.5、§9.8、§4.3 Disconnected）显式建模"限时自治 + 重连对账"；非 Endorsed 路径严格 Default-Deny（详见 P17.2 悲观推定）。
- **备选方案**：（a）仅靠 Endorsed_Mandate；（b）引入"区域级 RR 缓存"；（c）严格 Default-Deny 不开任何例外。
- **决议状态**：部分决议（Endorsed_Mandate 已落地于 §7.5）；离线策略上限待 Q11 决议。

### Q8 子代理"补充等级"

- **议题**：G0 Emergency_Override 与 G1 Strict / G2 Moderate / G3 Loose / G4 Autonomous 的五级体系是否足够？
- **当前协议倾向**：1.0 维持五级（§7.1）；不引入 G2.5 等中间档。
- **备选方案**：（a）引入"半自主 + 可干预"中间档；（b）允许实现自定义子等级但映射回五档之一；（c）引入正交的 Endorsement Grades 子等级（已落地于 §7.5）。
- **决议状态**：部分决议（Endorsement Grades 已正交叠加于 G1–G4）；中间档维持 Open。

### Q9 撤销级联的边界

- **议题**：DELEGATE 的级联撤销默认值（`cascade=true`）在多层派生时的可视性如何保证？
- **当前协议倾向**：默认 `cascade=true`（§5.3.5）；可见性由 `RevocationVisibilityBudget` 约束（§9.7、P14 跨派生级联撤销）。
- **备选方案**：（a）按派生树深度差异化预算；（b）维持单一预算 + 推 / 拉双轨。
- **决议状态**：未决；待 conformance 测试摸高深层派生树的实测可见性。

### Q10 协议命名（已决议）

- **议题**：协议正式命名。
- **决议结论**：协议正式命名为 **Faying Protocol**（无独立缩写），版本号 `Faying Protocol/1.0`。
- **决议状态**：已决议；本议题留作历史记录，不再开放讨论。

### Q11 Endorsement 最大寿命上限

- **议题**：协议层是否规定 `endorsement.endorsed_lifetime` 的硬上限（如 ≤12h）？是否再按 grade 进一步收紧？
- **当前协议倾向**：附录 B 给出推荐值（默认 4h，软上限 12h，且不得超过 `Mandate.not_after − Mandate.not_before`，详见 P16.3 / P16.4）；硬上限留待 RFC 决议。
- **备选方案**：（a）协议层硬编码 12h 上限；（b）按 grade 差异化（如 G1 ≤ 1h，G4 ≤ 24h）；（c）维持推荐值不强制。
- **决议状态**：未决；与 Q7 离线策略耦合。

### Q12 双向 Faying 滥用防护

- **议题**：iFay 主动发起的 `FAYING_REQUEST` 是否需要在协议层强制速率限制（每 (HP, IF) 对每分钟最多 N 次）？速率限制是否纳入 `ConfirmationRateLimit` 同一预算？
- **当前协议倾向**：FAYING_REQUEST 频次纳入 `ConfirmationRateLimit` 同一预算（详见 §5.3.6、§9.10.7、P18.6）；超限按 §9.10.7 自动降级 / 暂停。
- **备选方案**：（a）独立预算 `FayingRequestRateLimit`；（b）按 grade 差异化预算；（c）维持当前与 ConfirmationRateLimit 共享。
- **决议状态**：部分决议（默认共享预算已落地于 §9.10.7）；阈值上限与是否独立预算待 RFC 决议。

### Q13 Behavior_Baseline 标准化

- **议题**：行为基线的计算口径粒度（按 `action` / `scope_used` / `risk_level` / `affected_resources`，或多维联合）是否在协议层统一规定？还是允许实现自由发挥但要求基线计算口径本身写入 Attestation Chain？
- **当前协议倾向**：实现自由发挥 + 基线计算口径本身写入 Attestation Chain，口径变更视为审计事件（§3.6 I-BBS-3 / P18.5）。
- **备选方案**：（a）协议层强制（按 action / scope_used / risk_level / affected_resources 多维联合）；（b）维持自由发挥 + 审计；（c）引入"基线 schema 注册中心"统一口径。
- **决议状态**：未决；与 Q5 ego-deviation 判定耦合。

### Q14 Atomic_Action 最小粒度的客观判定标准

- **议题**：何为"最小不可拆分的 action"在协议层的客观判定？是否引入"action lattice"使 `scope.actions` 与 RP 端动作集合存在可形式化对齐的最小粒度规约？
- **当前协议倾向**：协议层仅强制"一次调用恰好 1 个 Atomic_Action / `scope.actions` 不允许通配符"（P18.2 Atomic_Action_Strict）；最小粒度的客观判定留给 RP 与协议委员会按行业领域规约。
- **备选方案**：（a）引入跨 RP 通用 action lattice；（b）按 RP 行业（金融 / 医疗 / IoT）分别 lattice；（c）维持当前留白。
- **决议状态**：未决；与 §9.10.8 T7 可扩展槽配套讨论。
