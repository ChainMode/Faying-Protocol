## §1 Overview

本章では Faying Protocol が何であり、何を解決し、何を解決しないのかを述べる。すなわち、プロトコルの命名、技術スタック上での位置、8 項目の設計目標、OAuth／WebAuthn などの既存方式との役割分担、一文での定義、仕様の適用範囲と明示的な非目標、そしてバージョン管理と互換性規則である。本章を読み終えれば、後続の §2–§11 と付録で用いる用語や制約に拠り所ができる。

> 本文中の規則の後ろには、対応する EARS 細目条項の番号を `Trace:` として示す（出典は本仕様の要件ベースライン）。形式は `R<requirement>.<criterion>.<clause>` であり、要件の出所を遡って確認しやすくしている。

### §1.1 プロトコルの命名

プロトコル仕様の名称は **Faying Protocol**、バージョン番号は **Faying Protocol/1.0** と表記する。

このプロトコルに独立した略称はなく、略記が必要なときはフルネームを用いる。初期ドラフトでは "Faying Auth Protocol（FAP）" を用いていたが、現在は廃止済みである。新しい文書では `FAP`、`FAP/1.0`、`Faying Auth Protocol`、`application/fap+json`、`POST /fap/v1/...` といった旧表記は登場しない。外部資料で `FAP` に遭遇した場合は、Faying Protocol の旧称とみなせばよい。

### §1.2 プロトコルの位置づけ

> **Faying Protocol は TLS の上に位置するアプリケーション層の「継続的認可レイヤー」プロトコルであり、「人類原型がその iFay に対し、どのような在場状態のもとで、どの範囲について、どのグレードで、どの期間に認可するか」という一群の意味論を担う。**

- **TLS の下**：チャネルの機密性と相手側の身元は TLS 1.3（mTLS の選択利用を含む）が担い、Faying Protocol が作り直すことはしない。
- **OAuth/OIDC の傍ら**：OAuth はアプリケーションへの認可を、OIDC は身元アサーションを担うが、いずれも「一時的なトークン」モデルである。Faying Protocol は両者がいずれも解決しない問題を解決する——**継続的な代理 + 在場バインディング + グレード切り替え + 責任帰属の一意性**である。
- **WebAuthn の上**：WebAuthn / FIDO2 は Bootstrapping 段階で人類原型に「ユーザー在場」のハードウェアレベルの証明を提供する。Faying Protocol はその資格情報の形態を、派生信頼の根（root）として再利用する。

Faying Protocol は TLS を置き換えるものでも、OAuth を再発明するものでもない。TLS の上、業務意味論の下に位置し、**iFay のあらゆる対外行為**を Mandate 検証ゲートに通すことを強制する。本プロトコルのゲートを迂回する対外呼び出しはすべて Rogue Action とみなされ、トランスポート層より上・業務層より下のミドルウェアで拒否されなければならない。

### §1.4 既存方式との中核的な差異（一文版）

| 既存方式 | 解決していること | Faying Protocol が解決せねばならぬ未解決事項 |
| --- | --- | --- |
| OAuth 2.0 / 2.1 | アプリケーションのリソースへのアクセス認可 | 使い捨てトークン。グレードなし、在場なし、対称的な撤回なし |
| OIDC SSO | 身元アサーション（who） | 継続的な代理（acting on behalf of）がない。グレードがない |
| mTLS | チャネル両端の相手側身元 | 「誰がどのような在場状態のもとで誰に何を委任するか」を表現できない |
| JWT | 自己完結クレームの署名 | 失効なし、グレード意味論なし、長寿命と「対称的な撤回」が矛盾する |
| FIDO2 / WebAuthn | 人類原型のハードウェアレベル在場証明 | ログイン瞬間のみをカバー。iFay の継続的代理をカバーしない |
| Macaroons | caveats 付きの派生可能トークン | 在場バインディングなし、人類原型の明示的な見証なし |
| SPIFFE / SPIRE | ワークロード ID | ワークロード視点であり、人間の責任端がない |

Faying Protocol は上記いずれの方式とも競合しない——TLS の上、業務意味論の下で「人類原型 ↔ iFay」という一群の**専属的な意味論**を補完する。すなわち、継続的な代理 + 在場バインディング + グレード切り替え + 責任帰属の一意性 + 対称的な撤回である。

### §1.5 一文での定義

> **Faying Protocol = 「Mandate（token の代替）+ Presence Signal（在場信号）+ Attestation Chain（証言チェーン）+ Revocation Registry（撤回登録）」の四要素が TLS の上で協調して表現する、人類原型と iFay によって双方向に発起され、人類原型の明示的な認可によって発効し、継続的にキャリブレーションされ、対称的に撤回される認可契約。**

#### §1.5.1 双方向 Faying は HP の明示的認可によって発効する（中核命題）

Faying 関係（確立または調整）の発起は**双方向**である。

- **HP-initiated**：Human Prime（人類原型）は能動的に Faying を発起でき、BOOTSTRAP チャネルを通る（詳細は §2.4 Phase A、§5.3.1）。
- **IF-initiated**：iFay は能動的に Human Prime へ Faying を求めることができ（すなわち FAYING_REQUEST）、§2.4 Phase A0 → BOOTSTRAP の 2 ステップ経路を通る（詳細は §5.3.6）。

> **ただし、いずれの側が発起しようとも、Faying 状態の変化が最終的に発効する条件は、Human Prime が明確で、欺かれておらず、検証可能な認可確認を与えることである**（既定の形態は WebAuthn のユーザー在場アサーション、または同等のハードウェアレベルの証明）。

ここから直ちに、本プロトコルの 3 つの越えてはならないハード制約が導かれる。

1. **iFay 自身は Faying 発効の条件を構成しない**：iFay が能動的に発起した FAYING_REQUEST が `BootstrapTimeout`（既定 60s、詳細は付録 B）以内に HP の明確な認可を得られなければ、期限切れまたは拒否となり、**いかなる Faying 状態の変化も生じない**。Mandate_Service は `E_FAYING_REQUEST_NOT_CONFIRMED`（エラーコード 1014）を返さなければならず、当該イベントを Attestation Chain へ書き込んで「どちらが発起し、いつ確認され、発効したか否か」という不可逆の証拠を保全しなければならない。
   - **Trace**：`R1.3.2`（IF-initiated 経路は HP の明確な認可確認後にのみ発効する）、`R1.3.3`（`BootstrapTimeout` 以内に認可されなければ拒否し、状態変化を生じない）、`R1.3.4`（発効の有無にかかわらず AC へ書き込む）。
2. **代替の見証経路は存在しない**：プロトコル層は、iFay、Mandate_Service、Supervisory_Agent が Human Prime に代わって Faying の認可確認を完了する正当な経路を一切提供しない。`human_witness` を欠く、あるいは `human_witness` の検証に失敗したいかなる BOOTSTRAP も、`E_HUMAN_WITNESS_REQUIRED`（エラーコード 1010）で拒否しなければならない。
   - **Trace**：`R1.3.5`（IF / MS / SA が HP に代わって Faying の認可確認を完了する正当な経路を提供しない）。
3. **撤回を iFay が一方的に迂回することはできない**：iFay は「Faying の切断を求める」メッセージ（Disclosure_Report とみなす）を発起できるが、自身の Mandate を撤回する権限は持たない。いかなる撤回も、最終的には Human Prime またはコンプライアンス上の権威機関が発起し、HP ビューチャネルを通じて可視でなければならない（詳細は §4 / §10）。
   - **Trace**：`R4.1.4`（IF は自身の Mandate を撤回する権限を持たない）、`R4.1.5`（切断要求は Disclosure_Report として AC へ書き込み、HP ビューへプッシュする）。

本款は §2.4 Phase A0、§5.3.6 FAYING_REQUEST、§5.4 エラーコード 1010 / 1014 を Overview レベルで統一するアンカーであり、後続の章における「HP の見証なくして Faying なし」に関するすべての論証の起点でもある。

### §1.7 バージョン管理と互換性

本節は Faying Protocol のバージョン番号付けの**権威的定義**である。バージョン番号は単なる文書上の印ではなく、**相互運用契約の一部**である——ワイヤエンベロープ、schema、ネゴシエーションビットに現れ、2 つの独立した実装が対話できるか否かを直接左右する。したがって本節は Normative であり、実装者は本節の規則に従ってバージョン番号を解釈し、バージョンネゴシエーションを実行しなければならない。付録 C の変更履歴は歴史を記録するのみで、規則を重複して定義しない。

#### §1.7.1 3 本の直交するバージョン軸

Faying Protocol は**互いに独立した 3 本の軸**で 1 つの仕様のバージョンを記述し、3 者を 1 つの番号に混同してはならない。

| 軸 | 答える問い | 形態 | 担い手 | 例 |
| --- | --- | --- | --- | --- |
| **プロトコルバージョン**（相互運用契約） | 2 つの実装が対話できるか | `MAJOR.MINOR` | 散文 / ワイヤエンベロープの `version` フィールド / schema ファイル名 | `Faying Protocol/1.0` |
| **文書ステータス**（ライフサイクル） | この仕様は確定したか | 列挙 | front matter の `status` | `Draft` / `Final` / `Deprecated` / `Obsolete` |
| **編集版次**（正誤訂正と明確化） | 同一プロトコルバージョン配下の何回目の文面改訂か | 公開日 | 公開ディレクトリ名 / front matter の `date` | `2025-10-25` |

> **中核制約**：**「プロトコルバージョン」`MAJOR.MINOR` のみがワイヤフォーマットに入る**（エンベロープの `version` フィールド、schema ファイル名）。文書ステータスと編集版次はワイヤフォーマットに入って**はならない**——これらは文書ガバナンスの印であり、相互運用の判定には関与しない。実装は、相手側の文書ステータスや編集版次が異なるという理由で、そのメッセージ処理の挙動を変えては決してならない。

#### §1.7.2 プロトコルバージョン `MAJOR.MINOR` の意味論

プロトコルバージョン番号は `Faying Protocol/MAJOR.MINOR` と表記し、**2 段階のみで PATCH 桁を設けない**——ワイヤフォーマットと相互運用意味論は 2 段階の互換性しか区別しない。

- **MAJOR（破壊的変更）**：旧版仕様に厳密に従って実装された相手側に、新しいメッセージを**拒否または誤解**させるような変更。例：§4.2 CDDL 権威 schema のフィールド意味論の変更、メッセージ型の削除、エラーコード意味論の再定義、状態機械の吸収状態の変更。
  - 規則：MAJOR を繰り上げ、MINOR をゼロに戻す（例：`1.4 → 2.0`）。
  - 互換性：異なる MAJOR の間では相互運用を**保証しない**。
- **MINOR（後方互換の追加）**：新しい実装が旧メッセージを理解でき、旧実装が認識できないオプション項目を安全に無視できるような追加。例：オプションフィールドの追加、メッセージやエラーコードの新設、AI-Era 脅威カタログ項目の追加、付録パラメータの追加、Correctness Property の追加。
  - 規則：MINOR をインクリメントする（例：`1.0 → 1.1`）。
  - 互換性：同一 MAJOR 内では、高い MINOR が低い MINOR に対する後方互換性を**維持しなければならない**。

**判定基準（実装者の自己チェック）**：その変更は、旧版仕様に厳密に従って実装された相手側に、新しいメッセージを拒否または誤解させるか？

- させる → **MAJOR**。
- させないが、ワイヤフォーマット上で可視な内容を追加した → **MINOR**。
- 文面のみを変え、ワイヤフォーマットの意味論をいっさい変えない（typo 修正、例の補足、曖昧さの明確化）→ **プロトコルバージョンを変えず**、§1.7.4 の編集版次で扱う。

現在のベースラインは `Faying Protocol/1.0` である。

#### §1.7.3 バージョンネゴシエーションと互換性規則（Normative）

バージョンネゴシエーションは **§6.1 アルゴリズムスイートのネゴシエーションと同じ流儀を再利用する**（各自が宣言し、共通でサポートする最高値を取る）。実装は次に従わなければならない。

1. **宣言**：BOOTSTRAP 段階で、クライアントとサーバーは各自がサポートするプロトコルバージョンの集合を宣言する（例：`supported: [1.0, 1.1]`）。
2. **同一 MAJOR では最高 MINOR を取る**：双方の MAJOR が同一のとき、両者が共通でサポートする**最高 MINOR** を当該セッションの発効バージョンとして選択しなければならない。高い MINOR の実装は、低い MINOR の相手側にサービスできなければならない（`MAJOR.0` まで後方互換）。
3. **MAJOR をまたぐ場合は拒否**：双方に共通でサポートする MAJOR が存在しないときはネゴシエーションを行わず、`E_PROTOCOL`（エラーコード 1099）で当該 BOOTSTRAP を拒否しなければならない。「ベストエフォート」で降格して相互通信してはならない。
4. **ローリングアップグレードは既存 Mandate を壊さない**：バージョンネゴシエーションによって新しい既定アルゴリズムスイートや新しい MINOR を導入する場合、既存の Mandate がその `not_after` 以前であれば依然として検証可能であることを保証しなければならない。バージョンアップグレードは、進行中の有効な Mandate を失効させてはならない。
   - **Trace**：`R8.2.4`（バージョンネゴシエーションによるローリングアップグレードが既存 Mandate の検証可能性を壊さない）。
5. **未知の高 MINOR の扱い**：同一 MAJOR でありながら、MINOR が自身より高いと宣言されたメッセージを受信したとき、実装は自身がサポートする最高 MINOR に従って解釈し、認識できないオプションフィールドは（拒否せず）**無視**しなければならない。これがまさに MINOR 後方互換の約束の実行時の落としどころである。

#### §1.7.4 編集版次と正誤訂正（Non-normative な変更）

`Faying Protocol/1.0` が確定稿（Final）となった後にも、**純粋な文面の正誤訂正**——typo 修正、例の補足、曖昧さの明確化、内部リンクの修正——は避けられない。この種の変更は次のとおりである。

- プロトコルバージョン番号を変えて**はならない**（さもなくば、相互運用契約が変わったと偽ることになる）。
- **公開日**を版次のアンカーとする。例：`Faying Protocol/1.0 (2025-10-25)` は 1.0 の最初の Final 版次であり、以降の正誤訂正は新しい公開ディレクトリ（例：`2026-03-xx/`）を生むが、プロトコルバージョンは依然 `1.0` である。
- 付録 C の変更履歴では `Editorial` カテゴリとして登録し、front matter では `edition` フィールドで版次の遷移を表示する。
- **ハード制約**：編集版次は Non-normative な変更のみを許す。ワイヤフォーマットの意味論に手を入れる修正は、いかなるものでも MINOR または MAJOR を上げなければならず、編集上の正誤訂正に偽装して公開して**はならない**。

#### §1.7.5 バージョン番号の落としどころと標準実装者の注意事項

下表はバージョン番号が各所に落ちる正確な位置を示す。実装者はこれに基づき「どの差異が相互運用に影響し、どれが影響しないか」を判断する。

| 落としどころ | 何を書くか | 注意事項 |
| --- | --- | --- |
| ワイヤエンベロープの `version` フィールド（§5.2） | `"Faying Protocol/MAJOR.MINOR"` | **MAJOR.MINOR のみを置く**。版次日付や文書ステータスは置かない |
| schema ファイル名（`fap-1.0.cddl` など） | `MAJOR.MINOR` に追従 | ファイル名は**編集版次で改名しない**——正誤訂正で `fap-1.0.cddl` を変えず、既存参照の安定性を保つ（初期の `fap` プレフィックスの保留も同じ理由、付録 C 参照） |
| content-type（§5.1） | `application/faying-protocol+cbor`（または `+json`） | content-type はプロトコルファミリーを識別する。ゲートウェイ層でバージョン別にルーティングしたい場合は `version=` パラメータを**デプロイ上の便宜**として付与できるが、当該パラメータはワイヤフォーマットの意味論には属さず、互換性判定に影響しない |
| front matter の `status` / `date` | 文書ステータス / 編集版次 | 文書ガバナンスの印であり、**ワイヤフォーマットに入らない**。相手側はこれに基づいてメッセージ処理を変えてはならない |
| git tag | `faying-protocol-v<MAJOR.MINOR>-<ステータス>` | 確定稿は `faying-protocol-v1.0-final`、版次スナップショットは `faying-protocol-v1.0-2026-03-xx`。tag は必ず本文 + `vectors/` + `schemas/` を同時にカバーし、相互運用の三点セットを一括で凍結する |

**標準実装者の必読注意事項**：

1. **相互運用の判定はプロトコルバージョンのみを見る**：「対話できるか」を決める唯一の根拠は `MAJOR.MINOR` である。相手側の文書ステータス（Draft/Final）、編集版次（公開日）はいずれも相互運用の挙動を**変えない**——相手側が Draft 表記である、あるいは版次が古いという理由で、その正当なメッセージを決して拒否してはならない。
2. **同一 MAJOR では後方互換が必須**：ある高い MINOR バージョンを実装するとき、`MAJOR.0` から始まるすべての低い MINOR の相手側に正しくサービスできなければならない。
3. **正誤訂正をアップグレードと取り違えない**：公開ディレクトリの日付変化（編集版次）はプロトコルが変わったことを意味しない。`MAJOR.MINOR` の変化のみが相互運用への影響評価を要する。
4. **schema ファイル名の安定性**：ファイル名に版次がエンコードされていることに依存しない。同一 `MAJOR.MINOR` の正誤訂正は同名の schema ファイルを再利用し、git tag / 公開ディレクトリで版次を区別する。
5. **Draft 期間は互換性の約束なし**：`status: Draft` の期間は、`MAJOR.MINOR` が凍結されないまま調整される可能性がある。`Final` 以降に初めて、本節の MAJOR/MINOR 互換性の約束が完全に発効する。
